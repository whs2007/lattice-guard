# 实现

## 触发
拿到 `【进入开发】` 令牌后进入 `IMPLEMENT`；评审发现阻断后进入 `PATCH`。

## 必做

1. **先读后写**：把要改的函数、它的调用方、相关测试全部读完，再动手。`findings.md` 里列出读过的文件与调用关系。
2. **先计划后改**：`plan.md` 写「改哪些位置 + 如何验证」。计划不是流水账，是给评审看的地图。
3. **最小改动**：只改达成方案所必需的地方。行数越少越好，不需要动的抽象一律不动。
4. **补测试**：行为变了必须补用例。用例要能证明「旧代码失败、新代码通过」。
5. **偏离要报**：实际做法与原计划不一致时，写 `plan-delta.md`（原计划 / 实际 / 为何偏离）。没偏离就别写。
6. **提交才算改完**：收尾必须 `git add -A && git commit -m "<做了什么>"`。工作树里留着未提交的改动，等于没改——引擎会判「改动不可交付」并暂停，因为提测第一步的 `merge` 只认提交。

## 产物

- `findings.md`：`## 读过的文件`、`## 调用关系`
- `plan.md`：`## 改哪些位置`、`## 如何验证`
- `plan-delta.md`（条件必填）：`## 原计划`、`## 实际`、`## 为何偏离`

## PATCH 阶段的额外约束

- **只修补 `review-report.md` 列出的问题**。评审没提的问题，这轮不许顺手改。
- 修补完仍要跑一遍测试，把结果写进下一次提测包。

## 反例
- ❌ 改代码顺带升级依赖。
- ❌ 改了 5 个文件，`plan.md` 里只写「调整相关逻辑」。
- ❌ 测试不过就把断言改宽。
