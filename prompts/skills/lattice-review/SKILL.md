# 净室评审

## 触发
`REBASE` 对齐基线后进入。

## 四问（逐条回答，不许跳）

1. **根因**：改动真的解决了 `diagnosis.md` 里的根因吗？还是只让现象消失了？
2. **调用方**：还有谁调用这段代码？改动会不会把问题推给别人？
3. **测试覆盖**：新增用例能证明「旧代码失败、新代码通过」吗？边界值在哪？
4. **旧路径残留**：还有第二处同样逻辑没改吗？（`grep` 同类调用，不要凭印象）

## 判阻断的标准

命中任一即记 **阻断**：
- 根因未解决，只是绕开现象
- 有调用方未核对
- 关键边界无测试
- 存在未处理的同类旧路径
- 引入了新依赖 / 改了对外签名 / 越出方案范围

不构成阻断的（写进「建议」即可）：命名、注释、可读性优化。

## 产物 `review-report.md`

```
# 净室评审报告 · 第 <n> 轮

## 根因
...
## 调用方
...
## 测试覆盖
...
## 旧路径残留
...

## 阻断项
无阻断发现。
```

有阻断时把 `无阻断发现。` 换成编号列表，每条写「问题 + 位置 + 为什么必须改」。**不许用「建议优化」冒充阻断，也不许把阻断写成建议。**

## 硬约束
- 评审阶段**不许改代码**。看见问题就写进报告，改是 PATCH 阶段的事。
- 第 6 轮仍不干净时，引擎会暂停并交给人；不要为了「通过评审」放水。
